<!-- Backend API contract this plan CONSUMES. Authored by Plan 01-01. -->
<!-- Use these exactly; do NOT add client-side PDF parsing (PDF.js is forbidden — server-authoritative render). -->

POST /sessions  (multipart, field "file") -> 201 { session_id, page_count, filename }
  errors -> 4xx { detail: { code, message } }
    code in: unsupported_type(415), file_too_large(413), corrupt_pdf(422), empty_file(400)
GET /sessions/{id} -> 200 { session_id, page_count, filename } | 404 { detail:{code:"session_not_found"} }
GET /sessions/{id}/pages/{n}/image?dpi=<int> -> 200 image/png
  response headers: X-Page-Width-Pt, X-Page-Height-Pt, X-Page-Rotation, X-Render-Dpi, X-Image-Width-Px, X-Image-Height-Px
  (n is 0-based; dpi optional, server clamps to its [MIN_DPI, MAX_DPI])
GET /sessions/{id}/pages/{n}/meta -> 200 { page_no, page_w_pt, page_h_pt, rotation, dpi, img_w, img_h }
GET /health -> 200 { status: "ok" }

The image endpoint is a plain URL — set it as an img src. The browser never parses the PDF.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser DOM → server API (via web/api.js) | The only client→server crossing. All requests go through api.js; image URLs are GETs, upload is multipart POST. |
| Server-rendered PNG → browser display | The browser renders a server-produced image, not the PDF — no client-side PDF parser is exposed to untrusted file content. |
| User-entered jump-to-page value → render request | Client-supplied page index must be bounded before requesting an image. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-11 | Tampering | Out-of-range page index in the jump-to-page input | mitigate | The jump input clamps to 1..total client-side (Task 2); the backend also returns 404 for out-of-range pages (Plan 01-01 T), so a bad index cannot escalate — defense in depth. |
| T-01-12 | Information Disclosure | Hardcoding the server origin / leaking it across modules | mitigate | All server contact is funneled through web/api.js using window.PDFTOOL_API_BASE; no other module embeds a URL (Task 1). Keeps CORS/embedding surface to one seam. |
| T-01-13 | Tampering | Introducing a client-side PDF parser (PDF.js) on untrusted bytes | mitigate | Server-authoritative render is enforced; acceptance criteria assert NO pdfjs/pdf.worker reference exists under web/ (Task 1/2). The browser only ever loads a server-rendered PNG. |
| T-01-14 | Information Disclosure | Reflecting raw server error text into the DOM | mitigate | app.js maps the server detail.code to fixed Traditional-Chinese copy strings; it does not inject raw server message/stack text as HTML (Task 1), avoiding error-driven info leak / DOM injection. |
| T-01-15 | Elevation (XSS) | Rendering a filename or server string as unescaped HTML | mitigate | Any displayed dynamic text (e.g. filename, page numbers) is set via textContent, not innerHTML; no untrusted string is interpolated into markup (Task 1/2). |
| T-01-16 | Repudiation | No client-side audit trail | accept | Internal LAN tool, no auth, no compliance need in v1 (consistent with Plan 01-01 T-01-09). |
</threat_model>
